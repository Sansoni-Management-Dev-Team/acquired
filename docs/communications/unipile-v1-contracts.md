## Accounts and IDs

- `GET /api/v1/accounts?cursor=...&limit=...`, limit 1–250. Instance schema: `{object:"AccountList",items:[Account],cursor,total_count,status_counts}`. Treat cursor as an opaque pagination token; no offset parameter. The inspected cursor schema is under-specified (`anyOf` empty schema/null), so do not invent a stronger provider guarantee. [Account list](https://developer.unipile.com/reference/accountscontroller_listaccounts)
- `GET /api/v1/accounts/{id}`: `{object:"Account",id,type,connection_params,sources:[{id,status}],...}`; type is uppercase, e.g. `LINKEDIN`, `WHATSAPP`, `GOOGLE_OAUTH`, `OUTLOOK`, `MAIL`. IDs are opaque nonempty strings, not guaranteed `acc_...`. Do not expose raw `connection_params` through public SDK/API responses. [Account lookup](https://developer.unipile.com/reference/accountscontroller_getaccountbyid)
- Source statuses are `OK`, `STOPPED`, `ERROR`, `CREDENTIALS`, `PERMISSIONS`, `CONNECTING`. Product/source association and initial sync need explicit evidence. Cached reads can remain available when synchronization has stopped; source `OK` alone does not certify exhaustive five-minute reply coverage. `CREATION_SUCCESS` starts sync, `SYNC_SUCCESS` finishes it, and LinkedIn classic/premium can produce separate product events. [Account lifecycle](https://developer.unipile.com/docs/account-lifecycle)

## Existing-chat messages and read-only reconciliation

`POST /api/v1/chats/{chat_id}/messages` accepts **multipart/form-data**. For the initial text-only transport, fields are `text`, `account_id`, optional `quote_id`. Always provide the recorded account ID: the vendor specifically documents that it prevents dispatch into another account's chat. Do not manually set a multipart boundary when using native FormData. Success is 201 `{object:"MessageSent",message_id:string|null}`. A null ID cannot establish a recoverable message receipt. No idempotency guarantee was found for this operation. [Send in a chat](https://developer.unipile.com/reference/chatscontroller_sendmessageinchat)

`GET /api/v1/messages/{message_id}` returns `object:"Message"`, Unipile `id`, `account_id`, `chat_id`, `chat_provider_id`, provider `provider_id`, `timestamp`, and numeric `is_sender`, `seen`, `delivered` (0 or 1). The instance also exposes optional `message_id`; it does not require that field. Account filtering is not a documented query parameter. Reconciliation must validate the returned recorded account/chat/ID; mismatched data cannot settle an unresolved send. [Message lookup](https://developer.unipile.com/reference/messagescontroller_getmessage)

`GET /api/v1/chats/{chat_id}?account_id=...` accepts Unipile or provider chat IDs; account ID is mandatory for provider chat IDs. Return fields include `id`, `account_id`, `provider_id`, numeric `type` 0/1/2 and `object:"Chat"`. Fetching the chat can validate scope before dispatch, but mutation between validation and send must still be prevented by the send's account field. [Chat lookup](https://developer.unipile.com/reference/chatscontroller_getchat)

`POST /api/v1/chats` **sends** while opening/reusing a conversation; it is never a harmless recipient-resolution method. LinkedIn requires an existing relation unless explicit InMail support is selected. Starting chats/attachments/group support remain separate capability work. [Messaging guide](https://developer.unipile.com/docs/send-messages)

## Email send and drafts

`POST /api/v1/emails` multipart payload requires `account_id`, `to`, `body`; optional `subject`, `from`, `cc`, `bcc`, `reply_to`, `custom_headers`, tracking and attachments. Addresses use `{identifier,display_name?}`; multipart structured fields are JSON strings. The guide also has an application/json example, but the instance schema advertises multipart only: use multipart initially. 201 response is `{object:"EmailSent",tracking_id:string,provider_id:string|null,provider_immutable_id:string|null}`. The immutable ID is Outlook-specific; tracking ID is not an email message ID. [Send reference](https://developer.unipile.com/reference/mailscontroller_sendmail)

The optional **email-only** `Idempotency-Key` is 1–255 characters, reuses the original result for identical/concurrent payloads and conflicts on changed payloads. Storage is memory-only for at most 24 hours, cleared on restart/maintenance. Preserve the service journal and unknown-outcome rules. `reply_to` identifies the parent email, rather than Reply-To address recipients. Plain text uses `Content-Type: text/plain; charset=utf-8` in custom headers. [Email guide](https://developer.unipile.com/docs/send-email)

The instance custom-header whitelist is `X-`/`x-` prefixes or `List-Unsubscribe`, `List-Unsubscribe-Post`, `Reply-To`, `Content-Type`. It does **not** establish support for caller-supplied `Message-ID`, `In-Reply-To` or `References`; reject those unsupported contract fields before I/O instead of dropping them silently.

`POST /api/v1/drafts` accepts the same multipart email shape and returns **200** `{object:"DraftCreated",draft_id:string}`. No draft update/delete/list operation appears in the instance OpenAPI or v1 reference index. Preserve unsupported capabilities explicitly; `PUT /emails/{id}` only changes unread/folders/Outlook categories and cannot replace draft contents. [Draft create](https://developer.unipile.com/reference/draftscontroller_createdraft), [Email update](https://developer.unipile.com/reference/mailscontroller_updatemail)

`GET /api/v1/emails/{email_id}?account_id=...&include_headers=true` accepts an Unipile ID or provider UID; account ID is required for provider UIDs. Instance variants distinguish reference, metadata and full bodies (`kind` `0_ref`, `1_meta`, `2_full`). Validate account and original UID; an incomplete variant cannot certify recipient/content facts. [Email lookup](https://developer.unipile.com/reference/mailscontroller_getmail)

Unipile `id`, provider `provider_id`, RFC `message_id`, Outlook immutable ID, and tracking ID are separate namespaces. Headers, sender/recipient arrays, folders, role and origin have distinct meanings. `read_date` is the first API retrieval date, not a recipient read receipt. [Email object](https://developer.unipile.com/docs/email-object)

## LinkedIn invitations

`POST /api/v1/users/invite` uses JSON `{account_id,provider_id,message?,user_email?}`. `provider_id` is the provider's user ID, not a profile URL/Unipile attendee ID; optional message max 300 characters in the schema. 200 `{object:"UserInvitationSent",invitation_id:string,usage?:number}`. This is an action receipt, not a message receipt; no invitation idempotency guarantee was found. [Invitation send](https://developer.unipile.com/reference/userscontroller_adduserbyidentifier)

Read methods: `GET /api/v1/users/invite/sent?account_id=...&cursor=...&limit=...` (limit 1–100, `{object:"InvitationList",items,cursor}`); `GET /api/v1/users/relations?account_id=...` (limit 1–1000); `GET /api/v1/users/{identifier}?account_id=...` for provider/public identifiers on LinkedIn classic. Pending absence does not prove acceptance. [Sent invitations](https://developer.unipile.com/reference/userscontroller_listalluserinvitationssent), [Relations](https://developer.unipile.com/reference/userscontroller_getrelations), [Profile](https://developer.unipile.com/reference/userscontroller_getprofilebyidentifier)

The v1 `new_relation` webhook can lag **eight hours**. Acceptance of a noted invitation can produce a self-sent message/chat, while a recipient may reply without accepting. Verify a positive relationship before branching; never count the user's own invitation as an inbound reply. [Acceptance detection](https://developer.unipile.com/docs/detecting-accepted-invitations)

## Webhooks: v1 is a different authentication contract

V1 documents a configured static secret header (e.g. `Unipile-Auth`), not the v2 HMAC signature. Keep authentication implementations version-specific. Use a separate webhook secret and constant-time equality, restrict target accounts, persist durable ingress before acknowledging, and deduplicate/replay independently: a static header provides no signed timestamp/replay protection. These persistence requirements are our policy, not an extra vendor promise.

`POST /api/v1/webhooks` is JSON with required `request_url`, `source`; optional `format:"json"`, `account_ids`, `headers:[{key,value}]`, `enabled`, `events`, `data` field-renaming configuration. 201 `{object:"WebhookCreated",webhook_id}`. Specify both authentication and JSON content headers; API-created webhooks do not supply JSON content type by default. Vendor guidance requires **200 within 30 seconds**, with **five** retries and unspecified incremental delays. No registration occurred. [Webhook overview](https://developer.unipile.com/docs/webhooks-2), [Create webhook](https://developer.unipile.com/reference/webhookscontroller_createwebhook)

- `source:"messaging"`: `message_received`, `message_read`, `message_reaction`, `message_edited`, `message_deleted`, `message_delivered`. Envelope fields include `event`, `account_id`, `chat_id`, `message_id`, timestamp, sender/attendees, `account_info`; `message_received` includes outgoing device/API messages. Compare sender provider ID to account owner and preserve explicit `is_sender`; first connection does not replay old history, reconnection can replay missed messages. [Message webhook](https://developer.unipile.com/docs/new-messages-webhook)
- `source:"email"`: `mail_received`, `mail_sent`, `mail_moved`; payload has account/email IDs and sender/recipient metadata. Sent mail and moves cannot automatically become inbound replies. [Email webhook](https://developer.unipile.com/docs/new-emails-webhook)
- Other sources include `users` (`new_relation`), `account_status`, `email_tracking`, `calendar_event`. Messaging/email examples lack guaranteed global event IDs; `email_tracking` has an `event_id`. Do not import the v2 `evt_` envelope assumption. Synthetic ingestion should preserve account/event/entity/timestamp data for durable deduplication and tolerate out-of-order events without certifying fresh coverage.

## Hosted setup follow-through (2026-10-13)

The [hosted-link API schema](https://developer.unipile.com/reference/hostedcontroller_requestlink) offers `single_use` on account-creation links; its documented default permits reuse. Creation now explicitly sends `single_use: true`, with five request assertions failing before the change and103 scoped hosted-auth/setup regressions passing afterward. Reconnect payloads retain the recorded account and do not add the creation-only property. This is documented-contract/fixture evidence, not a live link-creation test.

The [hosted-auth guide](https://developer.unipile.com/docs/hosted-auth) documents callback `status`, `account_id`, `name` and an example query capability on `notify_url`. We treat `name` as correlation, not authentication. Hosted-link parameters have no custom-header/signing configuration; custom secret headers belong to [regular webhooks](https://developer.unipile.com/docs/webhooks-2). Existing authenticated-notification test ports are synthetic application/gateway authority and do not imply native hosted callbacks emit their Bearer header. Runtime callback authentication must be composed explicitly; browser exposure of notification parameters is not specified. No callback endpoint or account binding was enabled.

[Exact account reads](https://developer.unipile.com/reference/accountscontroller_getaccountbyid) expose channel-specific self fields; [own-profile reads](https://developer.unipile.com/reference/userscontroller_getaccountownerprofile) expose additional LinkedIn/email identity fields. Account display names do not establish physical identity or app ownership. LinkedIn identifier namespace equivalence, WhatsApp phone formatting, verified alias/delegated-mailbox semantics and canonical IMAP mailbox identity still require concrete verification. Do not guess these bindings from a callback account ID.
