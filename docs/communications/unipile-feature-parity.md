# Unipile feature parity and additional capabilities

Reviewed 12 October 2026 for P0.3/P3.3/P3.5/P4.3/P4.4 against Acquire base `fa544da5578375efd57af4ba680a403a1568769e` plus the local communications foundation. This is a source/documentation audit, not live feature certification. No migrations, account connections, provider writes or deployments occurred in this review.

Unipile documents the principal communication operations and a wider feature surface than Acquire currently exposes. Full behavioral parity is **not yet established**. Email draft update/revocation and original RFC recovery, WhatsApp history/identity semantics, and fresh complete reply coverage are material unresolved gates. Existing backends remain necessary until these gates are satisfied or a deliberate capability limitation is accepted.

DigitalOcean hosts our current channel containers; Baileys, browser/private LinkedIn endpoints and direct Gmail provide their functionality. [WhatsApp hosting](../../ops/whatsapp/README.md), [LinkedIn hosting](../../ops/linkedin/README.md). Unipile can take over provider connections/session transport. The reusable service and Acquire still need ownership, durable operations, business rules and application hosting. This does not establish that DigitalOcean can be removed or that hosted Unipile is cheaper/faster/more reliable.

## Evidence and scope

Read the official [documentation index](https://developer.unipile.com/llms.txt), [provider feature matrix](https://developer.unipile.com/docs/list-provider-features), relevant account/authentication, messaging/history, email/draft, webhooks, limits, LinkedIn and calendar guides/reference pages linked below. Compared delivered application/service code, rather than treating everything supported by the underlying Baileys/Gmail libraries as an existing product feature. This is a review of the relevant feature surface, not a claim to have read every unrelated vendor page.

The configured credential/DSN is **v1**; prior account-list validation returned HTTP 200 with zero accounts. V2 uses a separate account/dashboard and is currently described as beta. V2 features do not fill v1 gaps without separately verified configuration and adapter work. [V2 welcome](https://developer.unipile.com/v2.0/docs/welcome). The private instance OpenAPI snapshot inspected earlier contains 95 operations, only `POST /api/v1/drafts`, and multipart email requests; its hash and exact contracts are in [v1 investigation](unipile-v1-contracts.md). Public docs may evolve ahead of that snapshot.

In the tables, **documented** means the provider has a matching operation, **partial** means important semantics remain unresolved, **gap** means parity was not established in the reviewed docs/schema, and **application/service owned** means our code must preserve the behavior. None means live verified. The implemented Unipile slice currently covers bounded existing-chat social text/invitations, transport/normalization/authentication fixtures and required dispatch ports; it does not implement the entire matrix.

## Parity gates and verification sequence

### Proposed alternative for F04: application-owned drafts

The user proposed keeping drafts in the application database and calling normal email send only when delivery is authorized. This is feasible: Acquire already stores message content/state, and its current approval route additionally synchronizes a Gmail draft. Application-owned drafts would support edit and approval revocation without any provider draft API. Approval remains separate from dispatch; the send worker must use the approved immutable content version and original connection, recheck authorization/reply/suppression policy, and atomically journal/admit the operation. Editing an approved version invalidates that approval; concurrent edit/revoke versus dispatch needs a defined transactional boundary. Revocation cannot recall a message already submitted.

The behavior difference is mailbox visibility: an application-only draft will not appear in Gmail's Drafts folder or support manual editing/sending there. Preserve the existing direct Gmail synchronization path unless its behavior is separately changed. Model draft storage/synchronization separately from channel/backend so other projects can use the same service. This proposal could remove provider draft update/revocation as a requirement for the Unipile app-only workflow; it does not establish F03 lost-response recovery parity. It is recorded as a proposed design, not implemented or selected for existing Gmail connections.

1. P0.3 resolves F03/F04 from exact vendor contract evidence; until then the capability model must refuse unsupported recovery/draft operations and retain direct Gmail. Do not route an approved draft to send or silently use another connection.
2. P3.3 adds recipient/profile/relationship and first-chat behaviors (F07/F11–F13), with red tests for wrong owner/recipient/product, already-connected/pending states and lost responses. Existing fixture successes cover only their recorded slice.
3. P3.5 proves F05/F08/F09/F14/F15: initial sync, disconnect/reconnect, pagination, bounded/non-exhaustive history, all relevant folders/products, aliases and stale coverage. Preserve five-minute readiness and cross-channel holds; inability to certify coverage blocks sends.
4. P2/P5 test real PostgreSQL admission/journal/events and crash/concurrency outcomes for F16/F17 under specifically approved schema. Vendor email keys and webhook retries do not replace durable storage.
5. P4.3/P4.4 expose only proven operations and accurate backend-specific setup/health/defaults. Preserve legacy flows and recorded active bindings. Current UI contains older manual/disabled copy despite implemented gated backend workflows; reconcile it against actual capabilities.
6. Record each F row as documentation-reviewed, fixture-verified, live-verified and released separately in the progress record. A live account with known history is needed for channel validation; the existing empty inventory is insufficient. Keep X rows as optional backlog until selected.

Current decision: proceed with additive integration; do not describe Unipile as a fully interchangeable replacement yet. This audit adds traceability and concrete parity gates, without changing database approval, live operation or release scope.
