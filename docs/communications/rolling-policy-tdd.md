# Physical-account rolling send policy

P4.1/F17 build-first source handoff. Calendar hour/day quotas alone do not preserve a rolling24-hour allowance or Gmail's60-second spacing policy.

`checkRollingDispatchPolicy(client,accountId,{rollingDay?,minimumSpacingSeconds?})` is a read-only SQL helper for the original physical-account held transaction. The configured journal invokes it after fresh held application/source/coverage checks and before any calendar quota charge, new immutable admission receipt or dispatch CAS. Acquire supplies its explicit account daily cap as `rollingDay` and initially60 seconds for spacing; a zero cap remains disabled. Optional omission preserves the previous calendar-policy contract, never supplies a provider permit by itself.

The helper counts immutable service admission charges across applications, owners and retained generations for that physical account. It includes unknown application commits, rejected provider attempts and other charged outcomes conservatively; it never refunds them. The available rolling boundary is the cap-th most recent relevant charge plus24 hours, calculated with the database clock. Known completion spacing uses the later journal update boundary rather than pretending the earlier service admission was the actual provider send. Inflight/unknown evidence includes its original claim deadline, and unresolved charged work returns review rather than authorizing a different operation. No caller-generated sent timestamp, wall-clock counter or backend-specific second allowance exists.

Denial returns a database-derived `waiting/rate_limited` retry time. The journal aborts held application permission and rolls back without quota/ledger/CAS writes. Unknown/missing/corrupt SQL proof cannot permit dispatch. Definite application commit is still required before a provider call. The SQL client/physical lock/current restricted role are trusted caller prerequisites; this helper is not a replacement for journal authority, held admission or global application quotas.

Tests were authored before the implementation:13 helper cases plus one journal composition case assert scope, DB-derived retry boundaries, unresolved/disabled behavior, rejected accessors/malformed proof and denial before every charge/permit. At the user's requested cadence these ran in the root combined batch and passed. No executed prechange RED is claimed for these batched test-first cases. Four actual PostgreSQL empty-inventory and charged blocked/rejected/skipped terminal ledger/role/clock characterizations are prepared in `src/db/communications-rolling-policy-local.integration.test.ts`, opt-in with the existing standalone/send-admission flags. It remains inert and unexecuted until standalone005 receives its specific approval and application. Approval-stage concurrent policy tests remain necessary for actual serialization certification; scripted rows cannot prove them.

A static review caught and corrected a virtual-versus-persisted state mismatch: the ledger stores blocked/rejected/skipped, whereas the core exposes completed. All charged terminal states remain counted without permanently rejecting their account proof. The single read-only SQL statement parses statically. No frozen migration, schema, startup or provider behavior was changed or executed. Existing dispatch admission timestamps/journal evidence suffice for this slice, so it introduces no migration. New service admissions do not fabricate historical pre-service charges, manual provider activity or unavailable send evidence; those limitations require explicit rollout accounting rather than invented backfill.
