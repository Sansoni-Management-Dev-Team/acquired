# P3.3 Unipile v1 email adapter: bounded send/read slice

Implemented on the feature worktree, 2026-10-14. This slice is locally verified with synthetic providers; it is not enabled in Acquire, registered for live dispatch, or live verified.

`communications/packages/adapter-unipile/src/v1-email.ts` composes the existing v1 account/email GET and email POST transport. It requires captured, trusted `verifyOwner` and `verifyOriginal` ports. There is no default mailbox owner, alias authority, original operation correlation, or database implementation. An `OK` account source proves transport health only. `ready` does not grant tenant send admission.

The adapter copies request/configuration data before asynchronous work, rejects accessor/proxy payloads, captures methods once, preserves the exact original binding, and checks the payload digest. Fresh sends have one canonical recipient and plain text. Replies resolve a recorded conversation to its recorded parent email ID, then verify the account, sender/recipient pair, RFC Message-ID/header, thread and subject through an account-scoped full-email GET. `reply_to` is the parent email ID; application `replyTo` becomes an address header. Group recipients, CC/BCC, arbitrary headers, attachments and caller-selected outgoing RFC IDs are unsupported in this slice. Vendor draft endpoints are unused; application draft approval remains separate.

The official [send reference](https://developer.unipile.com/reference/mailscontroller_sendmail) documents the v1 multipart endpoint, parent-ID field and a memory-backed idempotency key. The [email guide](https://developer.unipile.com/docs/send-email) supplies the plain-text header and reply subject examples. This adapter accepts the original subject or a `Re:` prefix; it never retries a mutation, even with the same key. No durable exactly-once guarantee is inferred from the provider key cache.

The current official [SDK send schema](https://github.com/unipile/unipile-node-sdk/blob/develop/src/mails/mail.send.types.ts) requires `EmailSent.tracking_id`. Earlier recorded instance schema also has nullable provider IDs. Tracking and message identifiers remain separate: `submitAcknowledged` returns an explicit `acknowledged` action receipt, including no invented submission time. This method performs a send; consumers must choose it or `submit`, never call both. Standard `MessagingAdapter.submit` returns `unknown` for this acknowledgement because the current durable message contract requires a verified message receipt. Optional provider IDs are not promoted into one.

Lookup accepts only an explicitly recorded message plus recipient and trusted original RFC evidence. It validates a full sent email and returns that original reference and source date. A missing original message is unsupported; there is no recipient/content search, automatic resend, or invented RFC correlation. A not-found read returns `null`, which is not proof of non-submission. Read-only lookup supports the original disconnected generation if trusted ownership evidence remains valid. The [retrieve reference](https://developer.unipile.com/reference/mailscontroller_getmail) supports both Unipile and provider IDs with account scope. The [official email schema](https://github.com/unipile/unipile-node-sdk/blob/develop/src/mails/ressource.types.ts) distinguishes those IDs, RFC IDs, tracking IDs, threads, role and headers. API `read_date` is not emitted as a recipient read receipt.

One monotonic overall deadline bounds account reads, ownership/correlation callbacks, parent reads and the single POST. Before a write, timeout/failure waits; after a possible write, it remains unknown. Rejected promises returned after synchronous overruns or accidentally supplied at synchronous configuration boundaries are observed without leaking their contents. Abort signals are supplied to cooperative ports; this does not cancel a provider action already accepted.

## Remaining runtime gates

Actual mailbox ownership/aliases and immutable operation correlation still require authoritative persisted implementations. A tracking-only accepted send needs durable `email_sent`/tracking correlation and verified original message/RFC evidence before completing a message journal; that correlation pipeline is not implemented here. Tenant admission, quota reservation, leases and durable dispatch are external mandatory composition. The current admission repository remains disabled. No registry, UI, account, webhook registration, migration, provider call, or deployment was activated. Gmail/Outlook/IMAP provider-specific live behavior remains unverified.
