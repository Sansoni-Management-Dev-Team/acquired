# Configured v1 account and notification runtime

This code composes the existing durable setup, retirement, tracking, dispatch, history and webhook boundaries. It uses Unipile v1, preserves application-owned drafts, and does not register webhooks, connect accounts, send live messages, apply SQL, or initialize a database. The service host remains responsible for verified application membership and held send admission.

## Bootstrap contract

`readConfiguredUnipileV1Environment(explicitEnv, sqlPool)` returns `{options, scopedAuthKey}` without reading process environment, dotenv, private files, SQL or a provider. Pass an explicit plain environment snapshot. Required names are `UNIPILE_API_URL`, `UNIPILE_API_KEY`, `COMMUNICATIONS_APPLICATION_ID`, `COMMUNICATIONS_INTEGRATION_ID`, `COMMUNICATIONS_PROVIDER_CONFIGURATION_REFERENCE`, `COMMUNICATIONS_ACTIVE_KEY_VERSION`, `COMMUNICATIONS_KEYRING_JSON`, `COMMUNICATIONS_IDENTITY_KEY`, `COMMUNICATIONS_IDENTITY_KEY_VERSION`, `COMMUNICATIONS_SETUP_CALLBACK_KEY`, `COMMUNICATIONS_SCOPED_AUTH_KEY`, `COMMUNICATIONS_WEBHOOK_SECRET`, `COMMUNICATIONS_REDIRECT_ORIGIN` and `COMMUNICATIONS_SETUP_NOTIFY_URL`.

Keyring JSON contains `{version,encryptionKey,digestKey}` with canonical base64 32-byte keys. Identity/callback/scoped keys must be distinct from each other and every keyring key. Retain original encryption/digest versions. The physical identity key is stable across encryption rotation; changing it is not an automatic identity migration. Keep the callback key stable until outstanding setup states expire. Optional product source IDs are explicit `COMMUNICATIONS_GMAIL_SOURCE_ID`, `COMMUNICATIONS_OUTLOOK_SOURCE_ID`, `COMMUNICATIONS_WHATSAPP_SOURCE_ID` and `COMMUNICATIONS_LINKEDIN_SOURCE_ID`; multiple account sources are never guessed.

`createConfiguredUnipileV1Runtime(options)` returns the management port (`list/setup/status/disconnect/setDefault`) plus:

- `authorizeSignedScope(scope,{expiresAt})`: trusted app-auth bridge only, bounded by the original signed expiry and DB time (maximum 60 seconds). Does not renew revoked grants. Callbacks cannot create grants.
- `completeSetupNotification({rawBody,capability})`: private notify-URL HMAC capability is nonce/expiry/integration/config bound. Resolves `queued` only after encrypted inbox commit. A fresh authenticated owner `list` poll verifies canonical owner and binds through the auth-state transaction. Browser redirects/hosted URLs establish no connection or readiness.
- `providerFactory(binding,{lookupOnly?})`: configured raw provider composition for the host's durable admission coordinator. `lookupOnly` preserves exact historical generation and rejects readiness/submission; it never selects a newer/default binding.
- `dispatchOptions(binding,{historical?})`: exact recorded vault/config and stable recipient digester, with tracking-backed original email reconciliation. Host adds the SQL pool, worker lease token and required held admission. `providerAccountDigests(binding)` supplies retained provider identity versions.
- `receiptDetails(binding,lookup,acceptedReceipt)`: exact read-only supplemental provider evidence for an original accepted receipt. No journal timestamp rewrite or resend.
- `createWebhookRuntime({captureCodec,journal,history})`: concrete encrypted integration spool and original claimed-work routing. `journal(binding)` must return the real scoped capture/claim/finish repository with tenant barrier; `history(binding)` returns `repository.recordInitialSync` and `normalizeWebhook`. Output is `{ingress,runOne,process,blocked}`. The host periodically invokes `runOne` with current membership/service authorization available; `blocked` joins readiness projection. No app imports or default admission exist.

`createSetupCallbackServer({runtime})` serves only POST `/v1/setup/notify?capability=...`, preserves bounded raw bytes and acknowledges only durable queued capture. Body/capture deadlines total less than 30 seconds; timeout returns retry and never implies canceled storage or late ACK. Capability/URL/body/private IDs/errors are not logged or echoed. The existing reply listener accepts `webhookRuntime.ingress`.

An optional trusted `readiness(binding)` callback projects actual stored history/coverage and pending-work evidence; the default connected result is `waiting/incomplete`. Unipile source OK is not initial sync/history/admission proof.

## Canonical ownership and messages

Gmail/Outlook primary mailbox identity comes from authenticated own-profile email and exact account/provider-owner corroboration. Gmail aliases require accepted verification. WhatsApp physical owner is exact E164 account phone; LinkedIn physical owner is the authenticated member ID, with canonical public profile separate. IMAP username/server data does not prove mailbox address, so configured IMAP setup remains rejected until that proof is available. Historical generations never inherit the successor's connected/active/default state.

Social first messages use one documented multipart POST `/api/v1/chats` with account/text/one verified attendee; this atomically creates the chat and sends text. Existing chats require exact owner/recipient/attendees/account proof. No empty-chat POST, lost-response search, resend or idempotency assumption exists. Exact returned message IDs get read-only chat/message evidence for actual timestamp before journal completion. A stalled/failed read retains acknowledged IDs without a fabricated timestamp. Invitation time comes only from the exact original pending sent invitation's valid `parsed_datetime`. Supplemental receipt lookup does not mutate immutable accepted facts. Numeric WhatsApp PN JIDs map to documented E164; undocumented LID identity is not guessed.

Email send acknowledgements remain distinct tracking/action IDs. The configured producer durably records the tracking ACK, then returns unknown. Authenticated `mail_sent` is correlated to that original reserved operation, canonical recipient/RFC/thread/known-message facts and a full outbound email GET with exact owner/headers/date. Only an established real email message receipt can reconcile the original unknown journal. No key is automatically changed and quota is not recharged.

## Prebinding notifications

The official v1 webhook guide guarantees five retries, so SYNC/reply events can precede owner binding. The encrypted spool records original bytes/time/config with no invented generation; 200 means durable passive integration receipt only. Already-recorded accounts are pinned to their real generation and coverage invalidated under the tenant fence in the same capture transaction. A new verified bind pins matching unbound receipts. Scoped routing preserves original time/bytes, proves the committed encrypted scoped inbox before clearing the spool, and processes the original claim. SYNC uses the checkpoint repository's authenticated original claim; sent events arriving before ACK remain retryable; other events use normal webhook normalization. Pending/review spool evidence blocks dispatch/reconnect/retirement; expiry preserves unresolved history rather than silently dropping evidence. Bounds are 262144 raw bytes, 512 pending receipts/config, 24 hour retention by default. Lost commits are retried with the same bytes/key; no provider action follows uncertain spool work.

Outgoing/self/verified-sent/email-sync ignores invalidate old complete cursor leases in the same scoped finish transaction without inventing a reply/person hold/outbox event. A new history scan supplies the actual recipient/contact evidence.
