# P3.3 durable email acknowledgement and verified sent association

This feature-tree slice is implemented with injected ports and scripted/native verification. Proposed standalone migration 004 and the actual PostgreSQL tests are **unapproved and unexecuted**. No startup invokes the SQL; this code is not registered in Acquire or enabled for sends. It does not provide complete email runtime recovery or production readiness.

## Producer and recovery composition

`createTrackedEmailSubmission({producer,tracking})` is the coordinator's optional email provider wrapper. It chooses the raw adapter's `submitAcknowledged` entry point once, validates the original action/recipient binding, awaits `recordAcknowledgement` through durable COMMIT and still returns `unknown`. Do not also call the raw adapter's `submit`: both entry points perform a send. Producer/callback mutation cannot replace the captured original snapshot. A send or COMMIT response loss never triggers another send or an acknowledgement retry.

`createPostgresEmailTracking(options)` requires the exact email/Unipile connection generation, integration/configuration, provider account and retained original-generation account decoder. Required cryptographic ports include the original journal codec, canonical recipient digester and an independent tracking-identity digester over integration/configuration/provider-account/tracking ID. Tracking identity is not operation-content-dependent. Every retained tracking key version must remain available; before inserting a new ACK, the repository checks persisted configuration-key inventory and all candidate digests. Account locking serializes duplicate/cross-operation and rotation checks.

`recordAcknowledgement({snapshot,trackingId})` requires an already reserved original journal in `dispatching`, `unknown` or `submitted`. It decrypts/authenticates the immutable original context and independently checks its recipient digest. It stores the tracking action separately, encrypted and HMAC-mapped. It never fills a journal message ID, changes unknown status, renews a claim/lease, reserves quota or admits work. One ACK belongs to one exact original journal; another tracking ID or another original operation is rejected conservatively.

`associate({snapshot,trackingId,notification:{rawBody,rawHeaders}})` first uses the required authentication port, then interprets only the documented v1 `mail_sent` pointer fields. The [official new-email webhook guide](https://developer.unipile.com/docs/new-emails-webhook) includes email, tracking, account and RFC IDs separately and also includes mail sent from other devices. This implementation requires the original recorded tracking ACK, `origin=unipile`, sent role, one intended recipient and empty CC/BCC. Open/click events and inbound/external mail cannot establish this association. The [tracking guide](https://developer.unipile.com/docs/tracking-email) describes open/click notifications, which are not used here.

The required `verifySentMessage` port must perform read-only verification against the original provider/configuration/account: mailbox owner, direct recipient, real sent message, RFC/header and original thread/message evidence. The authenticated webhook alone is insufficient. No default verifier or provider/account search exists. Missing original ACK returns `missing`: the upstream durable event must remain retryable, not be discarded as a completed correlation. The [email retrieve reference](https://developer.unipile.com/reference/mailscontroller_getmail) supports an account-scoped full-email read; the current raw email adapter can supply its existing ownership/header checks through authoritative recorded evidence, but concrete runtime composition is not enabled here.

After the provider read, the repository reacquires tenant, original connection/generation, physical mailbox, current grant, journal and ACK authority before recording an immutable encrypted association. The original known message, recipient, RFC and thread constrain the learned receipt. A different or replayed contradictory association cannot overwrite history. `get(snapshot)` reads the exact historical binding under current scoped authority, without initializing a reply barrier, renewing a lease or requiring the old generation to be current/active.

`verifyReconciliation(record,proposed)` is a read-only callback for the existing dispatch journal's trusted verifier. It returns a submitted message outcome only when the proposed receipt exactly equals an already committed association for that original unknown record. It does not transition the journal itself. The journal remains responsible for its own locks, current grant, reservation and evidence checks. IDs are learned receipt facts; original claim context remains immutable.

## Repository and migration boundary

Every transaction assumes a compatible injected driver; `release(error)` must physically retire/terminate the checked-out session, as the `pg` adapter does. Monotonic overall, statement and lock deadlines are bounded. Late connections/queries cannot issue a late COMMIT; active/uncertain sessions are retired instead of overlapping rollback with an in-flight query. Rejected promises at malformed library-input boundaries are observed. Provider/authentication ports receive abort signals but must remain read-only and cooperative; the SQL wrapper is not a sandbox for arbitrary trusted callback code.

Physical mailbox verification must be nonfuture according to the DB clock; no JS-clock inference is used. Current grants are share-locked and rechecked using the DB clock before every COMMIT, including reads before provider verification. The proposed SQL additionally checks authority immediately and through deferred INSERT guards at COMMIT. It enforces append-only ACK/association history, FORCE RLS, scoped reads, control-only SELECT/INSERT, restrictive FKs and no UPDATE/DELETE privilege. Tracking, account, recipient, message and RFC identifiers stay in authenticated ciphertext; SQL identity maps contain keyed digests. Stored digest/key versions are metadata, not secrets. No application aliases or memberships are repurposed.
