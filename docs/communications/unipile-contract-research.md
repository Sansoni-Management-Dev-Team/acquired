## Accounts, tenancy, and connection setup

The public platform schema specifies `GET /v2/accounts/` with response `{object,data,has_more}` and offset pagination; account retrieval is `GET /v2/accounts/{account_id}`. Account IDs have `acc_` prefixes. The account includes `application_id`, provider `user_id`, optional immutable `account_scope_id`, `provider`, `status`, `is_locked`, and product-specific connection states. `initial_sync` is an **object** containing `status` and optional `started_at`, despite the narrative guide describing it as a field with four values. Respect the endpoint schema. [Account reference](https://developer.unipile.com/v2.0/reference/getaccount)

Top-level states include `running`, `errored`, `disconnected`, `degraded`, and `partial`; individual products have `running`, `errored`, or `disconnected`. Compute readiness for the requested product plus lock/scope/permission checks. A nominally running account is insufficient by itself. The vendor application/scope is not a substitute for Acquire tenant/owner authorization.

`POST /v2/auth/link` has distinct variants: a new account requires `providers`, `expires_on`, `redirect_uri`; a reconnect requires `account_id` instead of `providers`. Provider names are lowercase (`google`, `outlook`, `imap`, `whatsapp`, `linkedin`). Optional `state` returns through redirect and account events. The callback's `account_id` is a pointer: fetch the account using the same API key and verify application, provider, identity, intended reconnect target, and ownership before binding. [Hosted authentication](https://developer.unipile.com/v2.0/docs/authenticate-with-hosted-auth)

Implementation policy: generate an opaque, single-use expiring auth-state record tied to the authenticated Acquire tenant/owner, requested platform, and expected connection generation; constrain redirects server-side. Provider callback fields cannot supply Acquire ownership. Callback and webhook races must consume the same state transactionally. Reconnect should invalidate coverage without clearing prior holds or uncertain actions. Vendor duplicate-account prevention is per application, so physical-account deduplication across workspaces, applications, and legacy backends remains our responsibility. [Account linking limitations](https://developer.unipile.com/v2.0/docs/link-an-account)

## Messaging, identity, and relationships

v2 messages are account **and chat** scoped; some providers only guarantee message ID uniqueness within a chat. Store references as `(backend,apiVersion,connectionGeneration,accountId,chatId,messageId)`, not one globally unique message ID. Reads use `GET /v2/{account_id}/chats/{chat_id}/messages/{message_id}`. Listing is per chat; v1's account-wide messages endpoint is removed. v2 message `id` and chat `id` are provider IDs. [Messaging migration](https://developer.unipile.com/v2.0/docs/migration-messaging-api), [message lookup](https://developer.unipile.com/v2.0/reference/getmessage)

Existing chat send is `POST /v2/{account_id}/chats/{chat_id}/messages/send`, requiring `text`, with optional `quote_id`, attachments, and provider specifics. A new WhatsApp chat uses `POST /v2/{account_id}/chats/send`; LinkedIn can require an inbox-specific start route. **Start-chat sends the first message** and is never an innocuous recipient-resolution check. [Message send](https://developer.unipile.com/v2.0/reference/sendmessage), [start chat](https://developer.unipile.com/v2.0/reference/startchat), [inbox start](https://developer.unipile.com/v2.0/reference/startchatfrominbox)

For WhatsApp phone lookup, use international digits plus `@s.whatsapp.net`; existing IDs can be `@lid` and should be reused exactly. A lookup may resolve a phone-number user or return 404; do not convert an opaque LID into an assumed phone. Starting a one-to-one conversation with an existing recipient sends into the existing conversation. Multiple attachments can fan out into multiple messages and a separate text message. Launch with the current text-only scope until this fan-out has explicit journaling semantics. [WhatsApp guide](https://developer.unipile.com/v2.0/docs/send-messages)

Profiles use `GET /v2/{account_id}/users/{user_id}`, with `me` for the owner; LinkedIn variants include classic, recruiter, and sales navigator. Do not assume the current `fsd_profile` URN is the v2 user identifier. [Profile reference](https://developer.unipile.com/v2.0/reference/getuserprofile)

LinkedIn invitations use `POST /v2/{account_id}/users/me/relation-requests` with `user_id` and optional message. The LinkedIn guide identifies the system ID as `ACo…`. Pending requests use the corresponding GET with `type=sent|received`; LinkedIn uses offset pagination. Already-connected requests fail. Confirm the relation and pending-request state before admission. Note a guide example for withdrawing incorrectly shows the accept URL; use the operation-specific endpoint reference/schema. [Invitation operation](https://developer.unipile.com/v2.0/reference/createrelationrequest), [LinkedIn invitation guide](https://developer.unipile.com/v2.0/docs/linkedin-manage-invitations), [pending requests](https://developer.unipile.com/v2.0/reference/getrelationrequestslist)

Relation events can lag six hours. Missing pending invitations can mean acceptance **or rejection**; establish the positive relation before an acceptance branch proceeds. An accepted invitation with text can generate a self-sent `message.new`, which must not count as an inbound reply. [Realtime delays](https://developer.unipile.com/v2.0/docs/realtime), [acceptance detection](https://developer.unipile.com/v2.0/docs/detecting-accepted-invitations)

## Email and draft parity

v2 listing is `GET /v2/{account_id}/emails`; sending is `POST /v2/{account_id}/emails/send`. Send payloads distinguish `plain_text`, `html`, recipient arrays, `reply_to` (Reply-To addresses), and `reply_to_message_id` (thread reply). Gmail/Outlook thread replies use provider message IDs; IMAP uses the RFC822 Message-ID. Custom headers override built-in fields case-insensitively. [Email send reference](https://developer.unipile.com/v2.0/reference/sendemail)

Draft creation is `POST /v2/{account_id}/drafts`; update is PATCH on `/drafts/{draft_id}`; deletion is DELETE on that path, returning 204. Creation must remain separate from send. **Outlook reply drafts are explicitly unsupported**. Updating attachments replaces existing attachments. Arbitrary custom-header support is documented for send but was not present in the inspected v2 draft fields: do not claim it until verified. [Create draft](https://developer.unipile.com/v2.0/reference/createdraft), [update draft](https://developer.unipile.com/v2.0/reference/updatedraft), [delete draft](https://developer.unipile.com/v2.0/reference/deletedraft)

v2 email IDs are provider IDs; RFC Message-ID is in headers. Folders are paginated and their IDs/roles must be synchronized. IMAP account-wide listing requires enabled initial sync; otherwise list folder emails. [Email migration](https://developer.unipile.com/v2.0/docs/migration-emails-api)

## Idempotency, receipts, and uncertain outcomes

v1 email POST supports `Idempotency-Key`: identical and concurrent requests share the result; changed payload gives 409 `errors/already_used`; keys are 1–255 characters, memory-only for up to 24 hours and lost at maintenance/restart. This is not durable exactly-once delivery and not evidence for v2 email, messaging, or invitations. No operation-specific v2 idempotency guarantee was established in this investigation. [v1 email idempotency](https://developer.unipile.com/docs/send-email)

Adapter policy: persist a scoped operation key plus account/generation/recipient/content fingerprint before dispatch. Never automatically retry a write after uncertain acceptance; expose `unknown` and reconcile read-only. A successful submit response certifies submission only. Match receipts against original account, chat, message, and recipient. Provider-shaped tests must cover late receipts, delivery-before-submit persistence, groups, and duplicate/out-of-order events. No request-by-operation-key lookup contract has yet been verified, so content/time matching alone must not settle ambiguity.

## Signed events and history coverage

v2 event envelopes include an `evt_` event ID, account/application/scope, creation time, type, and payload. `message.new` covers outgoing and incoming; `email.new` also covers sent mail and folder moves. Delivery/read are separate `message.receipt.*` events carrying chat/message/user IDs and timestamps. Bounce and draft events are distinct. Deduplicate by application/backend/event ID and retain original account references. Unknown future event types must not become replies. [Event reference](https://developer.unipile.com/v2.0/reference/event-types-1)

Verify raw body bytes with `unipile-signature`: `t=<unix-seconds>,v0=<hex-hmac-sha256>`, signing `<timestamp>.<raw-body>` using the endpoint secret; compare in constant time and impose a bounded timestamp window. Durably persist before 2xx acknowledgement within five seconds, then process asynchronously. Documented retries follow after 2 and 12 seconds; reconciliation is still required after exhausted retries. A registered endpoint secret is separate from the API key. No endpoint was registered here. [Webhook contract](https://developer.unipile.com/v2.0/docs/configure-a-webhook)

GET caching defaults to one hour. Use explicit `no-store`/`no-cache` or a justified maximum age for reply scans; inspect `Age`/`X-Cache`. A current HTTP response does not prove a current provider scan. Coverage needs source observation timestamps and an exhaustive boundary. [Cache guide](https://developer.unipile.com/v2.0/docs/caching)

WhatsApp requires initial sync; IMAP requires it for advanced search. Pending/running/failed sync cannot prove complete history; hosted-auth waiting is insufficient because users can leave early. [Initial sync](https://developer.unipile.com/v2.0/docs/initial-sync)

Email participant/text searches (`from`, `to`, `any_email`, `q`) can be approximate or incomplete, especially Outlook (~1000 results and missing matches). Use browse-mode date/folder traversal and known-thread retrieval where supported. Pagination differs by provider, and short pages are not necessarily terminal pages. No empty search response or webhook silence can certify five-minute coverage. [Email listing](https://developer.unipile.com/v2.0/reference/getemailslist)
