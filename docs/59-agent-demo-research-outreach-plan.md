### Existing authority and why a second demo receipt system is wrong

`communication_event_receipts` records authenticated subscriber delivery/disposition, including review/ignored incoming events. It is not a submitted-outcome ledger; campaign-role INSERT and a received/ACKed event cannot prove an original physical send. `communication_dispatch_permits` attests application admission, not submission. `communication_intent_resolutions` currently contains only authenticated **no-submission** proofs. The service's `operation_journal` owns encrypted, authenticated provider submission receipts. Its normal SDK original lookup already validates that receipt against the recorded snapshot, recipient and physical binding. None of these should be relabelled as positive facts, and the application must not manufacture a provider ID from an ACK.

Options:

1. Keep demo-specific receipt exceptions. This is bounded but duplicates authority, couples generic recovery to a feature mode, and makes other source types repeat the same logic. Rejected as the architectural destination.
2. Query/decrypt service SQL from every application domain trigger. This breaks the service boundary, couples schemas/keys and leaves several materializers independently responsible for receipt semantics. Rejected.
3. Add one reusable application communications submitted-receipt projection, populated only by the shared server boundary after normal SDK authentication of the **original** operation. Domain materializers consume that authority without submitting again. Recommended.

### Recommended shared contracts

`MandateExecutionContext` is a server-owned snapshot with explicit origin mandate, mode/demo namespace, current source contact fingerprint, effective recipients, permitted sender bindings/generations, mapping provenance and source-person identity scope. A SQL loader and matching TypeScript contract should be the sole origin/recipient policy. Real/no-mode uses genuine contact identities and existing ownership; demo uses the immutable mapping and exact dedicated registry or fails closed. No mandate inference from shared contacts, mutable labels, defaults, temporary contact rewrites or ambient client flags. Manual demo execution is disabled in V1 until a separately designed manual adapter exists; normal real manual/n8n use of the same contact remains valid.

A shared `CommunicationsSubmittedReceipt` projection should be keyed by original intent, retain source kind/source ID and original operation/effect, full recorded binding/generation, payload/source digests, canonical recipient, provider message **or action** reference, genuine submitted time, authenticated receipt digest and protocol version. It is mode-neutral and has no agent/campaign DML grants. A privileged, server-only writer resolves the immutable original intent, obtains the normal SDK receipt, checks `assertSubmissionReceiptMatches`, original payload/body/recipient/source revision and current membership, then appends idempotently under the held application gate. Network lookup happens outside the writer transaction; exact original/current source preimages are rechecked inside it. Unknown/null/mismatched lookup appends nothing, does not release holds and does not prepare a new epoch. An invitation action must never fabricate a provider message.

Materialization adapters for saved drafts, campaign attempts and native operations should compare immutable domain preimages with the original intent/projection and perform only terminal bookkeeping. They cannot approve content, activate an enrolment, advance a sequence step, choose another route, consume another permit, retry a provider write or overwrite an unknown with absence-based negative inference. Fresh send admission always resolves `MandateExecutionContext` again; original lookup and receipt reconciliation remain independent of current demo mappings or newer source edits. This separates permission to make a new effect from authority to record an existing effect.
