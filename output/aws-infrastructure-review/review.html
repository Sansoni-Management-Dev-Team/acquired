Moving Acquire’s infrastructure to AWS

Feasible, with research as the main engineering project. The Next.js app and channel services already have portable containers. PostgreSQL and n8n can move with careful preservation of state. Removing Cloudflare requires replacing durable execution, shared provider coordination, browser/search services, PDF conversion and caching. Plan approximately 25–40 engineering days for the full infrastructure move, before optional AI-provider changes.

The recommended destination is AWS Sydney (ap-southeast-2), preserving https://acquire.mlai.au. This is a proposed architecture and an engineering estimate, not a tested AWS deployment or a fixed quotation. No infrastructure was changed, database migration applied, workflow invoked, account connected or message sent during this review.

Live checks included DigitalOcean’s read-only API, SSH into the app host, selected nonsecret runtime configuration, PostgreSQL metadata/counts inside a read-only transaction, and n8n’s workflow-list API. Repository configurations and deployment records supplied the remaining context.

Recommended AWS destination

Start with an EC2/Compose move where it reduces work. Existing VM deployments can move to AWS without first adopting ECS. The managed target can use ECS Fargate for the app and WhatsApp, and EC2 or ECS on EC2 for browser workloads. Keep one app replica and one writer for each LinkedIn state shard until concurrency is addressed. EKS adds little value for the current footprint.

RDS PostgreSQL is the natural database target; there is no demonstrated need for an Aurora rewrite or Cognito adoption. Better Auth remains the identity system. Put app and database in the same region and consider same-AZ placement for the initial single-AZ footprint, accounting for the availability tradeoff. Add multi-AZ database and app redundancy if the required uptime justifies the cost and concurrency work.

The architecture above can remove DigitalOcean, Supabase hosting, Oracle hosting and Cloudflare runtime dependencies while retaining the current product integrations. Hosting n8n on AWS satisfies infrastructure consolidation; rewriting campaigns to Step Functions is a separate product/runtime project.

Work required by component

Application: mostly packaging and operations

  • Reuse ops/app/Dockerfile, standalone output, readiness checks and immutable release builds. Publish images to ECR; provision the service and ingress through versioned Terraform or CDK.
  • Replace host-specific deployment scripts and runner coupling with GitHub OIDC and scoped AWS deployment roles. Keep builds off small production hosts.
  • Load runtime secrets from Secrets Manager. Preserve the exact Better Auth, Gmail-token and channel encryption keys. KMS can protect those secrets; it does not automatically replace the existing application encryption format.
  • Keep the public hostname to preserve registered Google redirects and cookie identity. The current image checks build-time and runtime origins match; NEXT_PUBLIC_APP_URL is embedded during build.
  • Test long research/campaign callbacks, streaming, redirects, shutdown and readiness behind the chosen ingress. An ALB defaults to a 60-second idle timeout; some current callbacks allow 90–105 seconds. Configure and test this rather than relying on route maxDuration. AWS ALB timeout documentation.
  • Before increasing replicas, replace the process-local target-search guard with shared coordination and review Next.js caches/build consistency. Main and campaign pools currently permit five plus three connections per app process; include channel and n8n pools in the connection budget.

Database: small data volume, important permissions

The live database is PostgreSQL 17.6; use a compatible supported PostgreSQL 17 RDS release and test exact extension/collation compatibility. The application uses ordinary PostgreSQL, not Supabase Auth or its client Data API. Installed extensions include pgcrypto, uuid-ossp, pg_stat_statements, plpgsql and Supabase’s vault extension.

  • Prepare a scoped schema/data/role export for application-owned objects. Do not blanket-restore Supabase-managed auth, storage, realtime or vault services and roles into RDS. Decide how to preserve legacy neon_auth objects after a dependency inventory.
  • The limited catalog check found no public view/rule references into those managed schemas. It did not prove there are no function, trigger, dynamic-SQL, extension or external dependencies. Complete that inventory before excluding objects.
  • Explicitly preserve campaign roles, memberships, grants, RLS policies, SET LOCAL ROLE, advisory locks, sequence values and the Drizzle ledger. Both live campaign roles are non-superuser and non-BYPASSRLS. A table-only copy or generic restore that discards grants is insufficient.
  • Switch to the RDS endpoint and CA bundle; test certificate/hostname verification and reconnect. Direct PostgreSQL pooling is already supported; add RDS Proxy only if measured connection demand warrants it.
  • Rehearse restore and compare schema, row counts and content hashes. Test authentication, encrypted token decryption, tenant isolation, campaign replay prevention, WhatsApp leases and reply enforcement.
  • A scheduled write freeze is likely simpler than continuous replication at this size, but freeze duration must come from a rehearsal. Stop every writer, including channel/background processes and n8n. After RDS accepts writes, rollback requires reconciliation or transfer of those writes; changing the connection URL alone loses access to them.

RDS has its own administrative role model, so permissions must be validated on the target. RDS PostgreSQL roles. Every proposed schema/data migration, restore or role change requires the user’s explicit approval for that specific operation before execution.

LinkedIn and WhatsApp: preserve ownership and session state

LinkedIn: copy the encrypted /data volume and its exact key, preserving action journals, quotas, cooldowns, inbox checkpoints and browser session state. Use encrypted EBS with tested backup/restore and one active writer per state directory. Drain and stop the old owner before starting the new one. Test WebSocket/noVNC grants, framing policy and browser restore; a changed cloud egress IP may require fresh account verification.

EC2 is the lowest-friction initial target for LinkedIn and Chromium readers. Hosted configs request 1 GiB shared memory, while Fargate does not support the sharedMemorySize task parameter. LinkedIn already launches Chromium with --disable-dev-shm-usage, so Fargate is not categorically impossible; it needs separate memory, disk, viewer and persistence validation. Fargate task limitations.

WhatsApp: the Node service can run on EC2 or Fargate, continuously rather than in a short-lived function. Preserve its encrypted PostgreSQL data and encryption key, shard identity, leases and delivery journals. Drain sockets without logging out devices; allow lease ownership to transfer safely. Verify recovery without a QR rescan, including stale-owner fencing and unknown-send outcomes. Initial sizing should include adequate headroom beyond the present 512 MiB pilot.

For both channels, introduce stable owned service DNS names, update server-only URLs and maintain authentication. Keep existing send gates and uncertain-outcome handling during migration. Never run overlapping services against the same account merely to test availability.

n8n: move the runtime, not just workflow JSON

The repository compiles one n8n workflow per immutable sequence version and stores its IDs. Five active enrolments already depend on that runtime. Preserve the instance database, credential encryption key, workflow/webhook IDs, version information, waiting executions and external binary/custom-node storage where present. The production database backend and pinned n8n version still need direct host inspection.

A workflow export alone omits execution history and instance configuration. Full migration must preserve the underlying runtime state or explicitly drain existing executions on the original host. Avoid duplicating the minute scheduler or resuming waits twice. The public execution list alone is insufficient evidence that no waits exist. n8n backup and restore requirements.

The documented Oracle instance also contains an unrelated accounting workflow. Decide between moving the entire shared instance or creating an Acquire-only AWS instance and handling existing waits explicitly; do not move or delete unrelated workloads as a side effect. Initially retain the same n8n version/backend. A fresh initialization or version change can run built-in database migrations and also needs specific approval.

Two AWS constraints change the design. Standard workflows support long runs; Express is capped at five minutes and is inappropriate for 30–120 minute research budgets. Standard workflow state/task payloads are limited to 256 KiB, so put larger page/extraction payloads in S3 and pass references. Workflow types; Step Functions quotas.

Direct Step Functions HTTP tasks time out after 60 seconds, shorter than some existing 90–105 second callbacks. Use Lambda wrappers with suitable timeouts, ECS/activity workers, or an asynchronous task-token completion contract. Standard workflow semantics do not remove the need for idempotent side effects when an upstream request succeeds but its receipt is lost. HTTP task timeout.

Replace Cloudflare’s public-fetch guardrails explicitly for AWS browser/PDF workers: block private/link-local/metadata destinations, revalidate DNS and redirects, and restrict worker network access. Preserve existing evidence validation and budget checks. This is necessary deployment equivalence for a service that fetches arbitrary public URLs.

What “everything on AWS” can mean

All owned infrastructure on AWS: move compute, PostgreSQL, workflow hosting, coordination, caches, secrets, logs, backups and project DNS. External product integrations remain where they are: Google sign-in/Gmail/Places, LinkedIn, WhatsApp, Firmable, Apollo/ABN and AI providers where used. Hosting on AWS cannot replace those services’ identities, data or delegated accounts.

Optional provider consolidation: replace Resend password-reset delivery with SES and add a Bedrock adapter for AI. SES requires verified sending identities and production access outside the regional sandbox. Bedrock needs model/region availability checks and benchmarks against current structured extraction/drafting behaviour; it is not a model-name substitution. Keep Gmail for owner-delegated campaigns unless intentionally redesigning that product flow. SES production access.

Moving acquire.mlai.au DNS does not authorize moving the whole shared mlai.au zone. Route 53 delegation for project subdomains, or retaining parent DNS temporarily, needs an explicit ownership plan. Keeping Sydney persistence does not establish that every external provider processes data exclusively in Australia.

  1. Record live configuration, image identities, keys and backup ownership; inspect n8n waits/backend directly and collect representative CPU/memory/browser/DB/traffic metrics.
  2. Build AWS staging and move the app/channel containers first, preserving public app origin and existing provider contracts. Validate session restoration and release rollback.

  6. Observe, perform recovery checks and reconcile any post-cutover writes before retiring old services. Retire each provider only after its state and rollback obligations are resolved.

Cost and operational tradeoffs

Budget roughly US$300–700/month for a modest AWS-only footprint, or US$700–1,500+/month for a more redundant managed deployment with extra browser capacity. These are planning allowances, not a configured AWS quote or an upper bound. Assumptions: Sydney, about 730 hours/month, an always-on browser service comparable to the current 4-vCPU/8-GiB LinkedIn host, small app/WhatsApp/n8n services, modest research usage and log retention, no AWS credits/commitments, and external data/AI fees excluded.

AWS bills several items separately that bundled VMs obscure: NAT gateway hours and processing, public IPv4, load balancing, disks/snapshots, logs and network transfer. A low-cost EC2/Caddy pilot can avoid some managed ingress/NAT charges, at the cost of operating the hosts. Browser-heavy traffic and minute-by-minute workflow polling can materially exceed the allowance. Use explicit workloads in AWS Pricing Calculator before provisioning. EC2 pricing; Fargate pricing; Network pricing.

AWS should not be assumed cheaper. Its strongest benefits here are unified operations, private app/database connectivity, managed recovery options and IAM-based deployment. Prior Supabase investigations identified repeated large database reads as a likely egress contributor. Colocation can reduce public database egress, but migration does not repair inefficient queries or remove all network charges; use the existing research-db instrumentation to measure current behaviour.

Specific gaps to resolve before committing to a move

  • Recovery: DigitalOcean VM backups are disabled. That does not prove no other backups exist; inventory database, n8n, LinkedIn-volume and key backups, then prove restoration.
  • Inventory drift: docs/24-architecture.md still says Vercel/Neon, the October 7 plan understates LinkedIn capacity/cost, and the live campaign flags differ from older execution records. Update the authoritative inventory after the architecture decision.
  • AWS account readiness: account, IAM access, service quotas, Sydney service/model availability, billing/credits and existing networking were not inspected. No existing AWS deployment was assumed.
  • Actual workload: current peak CPU/RSS, browser saturation, campaign wait schedules, storage growth, database connection headroom, transfer volumes and full provider invoices remain unmeasured.
  • Migration scope: resolve shared n8n ownership, project DNS delegation, legacy schema retention, allowed downtime and whether multi-AZ recovery is required.
  • Live integration validation: retain the current campaign delivery safeguards, then validate intended account/session recovery and bounded research quality from AWS. Do not treat fixture success or a new VM’s health endpoint as production equivalence.
